# PRODUCT_DEBT.md — Known Inconsistencies & Target States

> The register of **known product/UX inconsistencies** — where the product diverges from the [Design System](../design/DESIGN_SYSTEM.md), the [architecture rules](../../AGENTS.md#9-architecture-philosophy), or the [product principles](PRODUCT_PRINCIPLES.md) — and the target state for each.
>
> **Context.** DalyHub V2 is a redevelopment of a prompt-driven V1. Much of the debt below is *inherited* from V1's patterns and is precisely what the V2 [roadmap](../roadmap/ROADMAP_V2.md) exists to resolve. As V2 is built greenfield on the shared foundation, resolving an item usually means "build the shared pattern instead of the legacy one." New debt discovered during V2 work is logged here too.

## How to use this register

- **Every entry links to a [ROADMAP_V2](../roadmap/ROADMAP_V2.md) item** that resolves it. Debt without a roadmap home is a signal the roadmap is incomplete — add the item.
- **When you touch code carrying debt,** either resolve it (and check the box) or update the entry with what you learned ([campsite rule](../../AGENTS.md#12-development-workflow)).
- **Found new debt?** Add it with the [template](#entry-template) rather than leaving it undocumented. Undocumented divergence is the worst kind.
- **Priority:** `P1` (actively harms coherence/trust), `P2` (notable friction), `P3` (cleanup).
- **Status:** ☐ open · ◐ in progress · ☑ resolved.
- **IDs are unique and stable.** Never reuse a retired number; never issue a number twice. The next free ID is **DEBT-108** (DEBT-107 was raised by the August 2026 UI quality audit — it had been issued as a SECOND `DEBT-101`, which this rule forbids, and was renumbered when the first DEBT-101 was resolved; DEBT-106 was raised by PEOPLE-04/DIARY-02; DEBT-105 is the AUDIT-11 half of DEBT-85, split out on resolution; DEBT-102…DEBT-104 were raised by the Today screen redesign; DEBT-101 was raised by EDIT-02; DEBT-99 and DEBT-100 were raised by M3-INT; DEBT-97 and DEBT-98 were raised by EDIT-01/DS-16; DEBT-95 and DEBT-96 were raised by the shell-polish change; DEBT-90 is now ☑; DEBT-90…DEBT-94 were raised by AI-01/AI-04; DEBT-79…DEBT-88 were raised by the [5 August 2026 end-to-end audit](END_TO_END_AUDIT_2026_08_05.md)).   - **Known ID collision, recorded rather than silently renumbered (UX-01, 2026-08-01).** The number **DEBT-45** was issued twice: once for *"A captured record is not linked to the context it was captured from"* and once for *"Keyset paginators can consume a revalidated fetcher page after a scope reset"*. Renumbering either would break every existing cross-reference, so both keep the number and each is identified by its title. Both are now ☑ (the pagination one on 2026-08-01, the capture-context one on 2026-08-08). Do not issue DEBT-45 again.
  - **A near-miss, resolved the other way (2026-08-08).** PEOPLE-04/DIARY-02 and AUDIT-11 both issued **DEBT-105** in parallel. - **Close only on evidence.** An entry moves to ☑ when the source code *and* its tests prove it, cited in the entry. "It should be fixed by now" is not evidence.

### ☑ UIQ-013 / UIQ-014 / UIQ-021 — collection view switchers, the Reviews primary action, and overflow-menu viewport placement — **RESOLVED 2026-08-07 (#130)**

- **Current issue (was).** Three findings the August 2026 UI quality audit recorded rather than fixed, because each needed a shared change too broad for an audit PR. **UIQ-013**: view switchers rendered four ways — the shared segmented control (Projects/Goals/Notes/Tasks), pill tabs under the header (People), pill rows inside the pane header (Assets/Reviews) and loose segment links in a content toolbar (Meetings) — three selected-state treatments, two corner radii, and three of the four below the 44px target. **UIQ-014**: "New Review" rendered beside the view pills instead of the shared primary slot. **UIQ-021**: the one shared menu always opened below its trigger with no max-height and no flip, so a ~713px Tasks row menu opened low on an 800px viewport ran past the bottom.
- **Resolved by.** One documented [collection-header anatomy](../design/DESIGN_SYSTEM.md#the-collection-header-anatomy-uiq-013uiq-014) with fixed semantic ownership of its slots; ONE [view switcher](../design/DESIGN_SYSTEM.md#the-view-switcher-uiq-013) (`~/shared/view-switcher`) that eight collections and Diary now render, with the `SegmentedFilter` wrapper kept for genuine in-content filters; the primary action in the shared slot on every collection, with an intentional two-row narrow composition instead of accidental wrapping; and viewport-aware flip/clamp/scroll placement in the one shared menu, with the decision logic as a pure, unit-tested function.
- **Also removed.** A `projects.css` rule that turned EVERY `.dh-segmented` in the product into a two-column grid below 30rem — a module stylesheet deciding how a shared primitive degrades, and the reason the four Review scopes rendered as a 2×2 block with the container's rounded ends mid-row.
- **Not done here.** UIQ-011 and UIQ-012 remained open. **UIQ-011 was then resolved by [#131](../design/RECORD_SCREEN_CONVERGENCE_2026_08.md)** — see immediately below; UIQ-012 is still open.

### ☑ UIQ-011 — Person record exposes eight equally-weighted actions — P3 — **RESOLVED 2026-08-08 (#131)**

- **Original issue.** The Person record's Summary carried eight tonal pills at one weight (Call, Email, New Task, Diary entry, New Meeting, New Note, Copy email, Copy phone), where the Quick Actions contract says a curated two or three live on the surface and the tail lives in the overflow and the Command Palette. A greyed-out Call on a person with no phone number was also a control that could never do anything.
- **Resolved (#131).** **Call and Email are the primary actions**, plus **Message** where the person has a mobile (`sms:` needs a mobile, not any phone — so someone with only a work number gets two actions, not a third that would text a landline). Each is rendered **only where the data behind it exists**: the sparse Person fixture renders no action group at all rather than a row of disabled buttons. The four capture actions and the two clipboard actions moved into the record header's shared DS-12 overflow, still carrying this Person's capture context (ADR-060) — nothing was removed from the product, and the copy entries are themselves omitted when there is nothing to copy.
- **And the surface around them.** The Summary had been restating the record header — the name, the pronouns, and "Site foreman · Whitfield Building Co." — so it read as a contact row with a button bar. Each of those facts is now stated once, in the header's context line, and the Summary keeps what the header cannot show: the person's face, their preferred name, and the relationship word. The stay-in-touch pill likewise appears once (the context line) with the panel explaining it rather than repeating it.
- **Evidence.** `e2e/record-anatomy.spec.ts` → "the Person action hierarchy (UIQ-011)": asserts exactly three exposed contact links on the full fixture, none on the sparse one, and every demoted action reachable in the overflow. Before/after captures in [`assets/record-2026-08/`](../design/assets/record-2026-08/).

### ☐ UIQ-012 — the Goal status "Open" reads as a command, not a state — P3 — **retained, with the reason**

- **Current issue.** A Goal card's status chip says "Open", which sits where every other card shows its ⋯ menu and reads as *"Open this record"* rather than as a state.
- **Investigated, and deliberately not renamed.** "Open" is not Goals-only vocabulary. It is the shared spine word for "not yet completed", used by the Goal chip (`goalStateLabel`), the Area's equivalent, the Goal search projection, and — decisively — by **Projects**, where `open` is a real `ProjectStateFilter` value in the repository, a documented segment (`All / Open / Completed / Archived`) and a **URL parameter** (`?state=open`) that is shareable and bookmarkable.
- **Why that settles it.** Renaming only the Goal chip would replace one inconsistency with a worse one: two different words for the same binary state on two sibling spine entities. Renaming both coherently means changing a domain filter value, a URL contract, the repository's typed state filter, the segment labels, the tests and the docs together — a vocabulary migration with a persistence-visible surface, which is exactly what this PR was told not to fold in. The audit's own instruction was to leave it recorded rather than guess.
- **Desired future state.** If the product decides "Active" is the clearer DalyHub-wide word, change it as one vocabulary change across Goals AND Projects — chip, filter value, URL parameter (with the old value still accepted), forms, accessibility labels, tests and documentation — not as incidental cleanup. **This needs the owner's decision, not an implementer's.**

### ☐ RECORD-02 — Two records have no Settings tab, so their paperwork has nowhere to be demoted to — P3

- **Current issue.** [RECORD-01](../design/RECORD_SCREEN_CONVERGENCE_2026_08.md) gives every record's administrative metadata (Created, Updated, raw State) one home: a shared `RecordDetails` list in the record's **Settings** tab. Seven records have one. **Goals and Notes do not.** The Goal's timestamps are therefore demoted to the trailing `facts` line of its summary band, and the Note's "Created" relies on its Activity tab's `entity.created` event plus the print byline. Both are the contract's permitted "later in the record" fallback, and both are correct — they are simply not the same answer the other seven give.
- **Why it was not done here.** Adding a Settings tab to a module changes that module's information architecture, which PR #131 was explicitly scoped out of. Adding one purely to host two dates would also be a tab that is almost empty on arrival.
- **Desired future state.** Goals and Notes gain a Settings tab when they have a second reason to (a Goal's icon, a Note's default tags), and their Record details move into it. Until then the fallback is documented rather than silently inconsistent.

### ☐ RECORD-03 — A Goal's summary is still the tallest on a phone — P3

- **Current issue.** At 1280×800 every converged record's working content clears the fold anchor with room to spare; the Goal is the tightest because its summary genuinely carries the definition of done, the contribution meter, the alignment state and its reasons. At **320–390px** those stack, and the Goal's Projects tab starts ~900px down.
- **Why it is recorded rather than fixed.** The contract's fold anchor is specified at 1280×800, and phone layouts are permitted to recompose. Nothing here is duplicated or wasted — it is real content in a narrow column. The honest fix is a phone-specific decision about whether a Goal's definition of done should be collapsed on first paint, which is a design question this PR had no mandate to answer.
- **Desired future state.** A decision on progressive disclosure for long record prose on phone widths, applied through the shared summary band rather than per module.

### ☑ DEBT-03 — Multiple save patterns (autosave vs. explicit vs. modal) — P1
- **Current issue.** Different forms save differently; users can't predict whether edits persist. Erodes [trust](PRODUCT_PRINCIPLES.md#how-users-should-feel).
- **Desired future state.** One [Forms](../design/DESIGN_SYSTEM.md#forms) system with a predictable save model per field type.
- **Resolution.** [DS-06](../roadmap/ROADMAP_V2.md#-ds-06--shared-forms--field-controls) delivers ONE shared [forms system](../design/DESIGN_SYSTEM.md#shared-forms--field-controls-ds-06) in which the save mode is a **declared, visible part of the component contract**, never inferred: `useForm` for explicit Save/Cancel (dirty tracking, duplicate-submit prevention, draft preservation on failure, unsaved-navigation interception) and `useAutosaveField` for calm, deterministic autosave (`Unsaved`/`Saving`/`Saved`/`Couldn’t save`, stale-response-safe, retry). No modal-save pattern is introduced. The predictable model now exists design-system-wide; each product create/edit surface simply adopts it (there are no product forms today that still diverge).
- **Related roadmap item.** [DS-06](../roadmap/ROADMAP_V2.md#-ds-06--shared-forms--field-controls).

### ☑ DEBT-39 — `[[Wiki Links]]` create no EntityLink, and the resolver scans the whole workspace — P2
- **Current issue.** REL-01's wiki links are resolved at **navigation** time: [`wikilinks.ts`](../../app/platform/markdown/wikilinks.ts) rewrites `[[Title]]` to `/notes/resolve?title=…` and [`notes/routes/resolve.tsx`](../../app/modules/notes/routes/resolve.tsx) finds a matching entity and redirects.   2. **The resolver is an unbounded read.** It pages through **every** entity in the workspace with a deliberate "no page cutoff" (documented in the route), stopping early only on a note match. That is a correct-but-unbounded scan on a hot navigation path, contrary to the [performance expectations](../../AGENTS.md#16-performance-expectations) every other read honours with bounded, cursor-paginated queries.
- **Resolved (2026-07-28, NOTES-02).** The decision this entry asked for was made and recorded as [ADR-054](../decisions/ARCHITECTURE_DECISIONS.md#adr-054-note-knowledge--a-wiki-link-is-a-persisted-reference-and-knowledge-relationships-stay-entitylinks): **a wiki link in a saved note is a persisted reference.** Both halves are closed.
  1. **A relationship is now written.** `reconcileNoteReferences` ([`note-references.ts`](../../app/platform/entity-links/note-references.ts)) makes the note's typed `note.references` EntityLinks exactly match the `[[…]]` in its body on every content save, so a referenced record shows the reference in its Backlinks and both records' Timelines carry the kernel's `entity_link.*` events. Titles are matched ONCE, at save time, and the relationship is persisted by **stable id** — renaming the target keeps it, which is why "no fragile title-based matching" and "renaming does not break links" are both true. Duplicates collapse to one row; a reference inside code is never a relationship; removing the last mention unlinks; re-adding restores the SAME link id rather than duplicating. Reconciliation only ever touches `note.references` links whose SOURCE is that note, so nothing a user created by hand is disturbed, and it never fails the save (the Markdown source is the canonical record).
  2. **The unbounded read is gone.** Title resolution is `NoteQueryRepository.resolveReferenceTargets` — ONE bounded, chunked, indexed `lower(title) IN (…)` query with a total, stable tie-break (a Note wins, then the earliest-created record) — instead of paging every entity in the workspace with no cutoff.

### ☑ DEBT-42 — Repository-backed searches can fail the whole query on a long user input — P2
- **Current issue.** D1 caps a `LIKE` pattern at **50 bytes**; a longer pattern fails the ENTIRE statement with `LIKE or GLOB pattern too complex: SQLITE_ERROR`, not just that predicate. Every repository-backed search builds its pattern as `%<user input>%`, so **any query over ~48 characters — a pasted title, a copied sentence — returns a 500 rather than results.** Found empirically while building the Notes search (a full note title as the query, reproduced end to end), not by inspection. [`d1-note-repository.ts`](../../app/platform/storage/d1/d1-note-repository.ts) now bounds the escaped needle itself, so a long Notes query degrades to matching its opening characters. **The same exposure remains** in `d1-person-repository.ts`, `d1-asset-repository.ts`, `d1-meeting-repository.ts`, `d1-review-repository.ts` and `d1-task-repository.ts`, each of which builds `%…%` from unbounded user input.
- **Impact.** A user pasting a name or a title into People, Assets, Meetings, Reviews or Tasks search gets a broken surface, not zero results — and the failure mode is a server error, which is the least honest possible answer to "I searched for something long".
- **Desired future state.** ONE shared helper for building a bounded, escaped LIKE pattern (the Notes implementation, promoted), used by every repository-backed search, with the truncation documented at the search surfaces. Truncation must never leave a trailing unpaired escape character, which SQLite rejects in its own right.
- **Related roadmap item.** [X-01](../roadmap/ROADMAP_V2.md#-x-01--global-search-maturity); [DS-08](../roadmap/ROADMAP_V2.md#-ds-08--shared-search).
- **Resolved (2026-07-29).** X-01 promoted the bounded LIKE helper to
  [`app/platform/storage/d1/like-pattern.ts`](../../app/platform/storage/d1/like-pattern.ts)
  and reused it across repository-backed Search projections, including the new
  Areas/Goals/Projects/Diary projections and the widened Tasks projection. The
  helper escapes `%`, `_` and `\`, bounds by UTF-8 bytes under D1's 50-byte pattern

### ☐ DEBT-44 — A held meeting appears on the timeline of a linked NON-attendee — P2
- **Current issue.** [MEET-03](../roadmap/ROADMAP_V2.md#-meet-03--people--history-integration)'s `meeting.held` names the Meeting as an Activity subject (so the Meeting's own Timeline carries it, and the Person timeline can link back to the canonical record). But a Person who is linked to that Meeting — by a `link.related`, or as an attendee added AFTER it was marked held — has the Meeting in their PEOPLE-02 anchor set, and `listForEntities` returns every event naming an anchor. So they see the line `<the person who marked it held> · Meeting held — <meeting>` on their relationship history even though their id is **absent** from the recorded attendee subjects.
- **Verified, not assumed (2026-07-28).** Raised by automated review on [#81](https://github.com/acedaly/DalyHub-V2/pull/81) and reproduced with a throwaway integration test against the real loader before being accepted: both a late-linked attendee and a `link.related` bystander receive the event, and the item's `subjects` array contains only the Meeting (`isAnchor: false`) — no Person.
- **Impact, stated honestly.** It is the PEOPLE-02 anchor contract working exactly as designed: a linked record's own events appear on your timeline, and `meeting.created` / `meeting.updated` already behave this way. The line is a true statement about the Meeting and disappears if you unlink. **But** "Meeting held" reads as *"we met"* in a way that "Meeting created" does not, so on a relationship history it is true-but-misleading for someone who was never an attendee — and it sits awkwardly beside MEET-03's own documented rule that a late-added attendee is "not retroactively added".
- **What is NOT affected.** The durable, Person-scoped fact is subject membership, and the [PEOPLE-03](../roadmap/ROADMAP_V2.md#-people-03--stay-in-touch-signals) contact seam reads `activity.listForEntity(personId)`, which returns only events naming that Person. So a non-attendee can never become a "last meaningful contact" through this. The defect is presentational, not a corruption of the contact signal.
- **Why it was not fixed in MEET-03.** The suggested remedy — filter `meeting.held` on the People read path — would put Meetings knowledge inside the People module, which MEET-03 explicitly forbids and which an architectural test asserts against. The architecturally clean fix is a **generic** People-timeline rule ("an event that names Person subjects appears on a Person's timeline only if that Person is one of them"), which carries no Meetings knowledge but **changes PEOPLE-02 semantics for every module's events** — e.g. a third party's `entity_link.created` would stop appearing. That is its own roadmap item, not a late addition to a shipped one (AGENTS.md §13, one item per PR).
- **Desired future state.** Decide the rule deliberately as part of [PEOPLE-03](../roadmap/ROADMAP_V2.md#-people-03--stay-in-touch-signals) or a dedicated PEOPLE item: either adopt the generic subject-membership rule (with tests and a documented PEOPLE-02 semantic change), or accept the anchor contract and make the distinction legible in the UI.
- **Related roadmap item.** [MEET-03](../roadmap/ROADMAP_V2.md#-meet-03--people--history-integration); [PEOPLE-02](../roadmap/ROADMAP_V2.md#-people-02--relationship-timeline); [PEOPLE-03](../roadmap/ROADMAP_V2.md#-people-03--stay-in-touch-signals).

### ◐ DEBT-47 — An open autosave editor does not adopt a server-side change to its field — P2

- **Resolved half (NOTES-05 knowledge completion, 2026-08-01).** The reconciliation contract the entry asked for now exists on the shared DS-06 coordinator, and it is exactly the shape described above: an external value is adopted **silently while the field is clean** (no pending edit, no in-flight save, no failed save) and **parked while it is dirty**, with the newer version OFFERED through the shared `RemoteChangeBanner` — take theirs, or keep mine. ### ☑ DEBT-45 — Keyset paginators can consume a revalidated fetcher page after a scope reset — P3 — **RESOLVED 2026-08-01**
- **Current issue.** Every "Load more" collection paginator follows the same shape: a `useFetcher`, an `appended` accumulator, and a `processed` ref that de-dupes by **object identity** so one response is applied once. Identity alone is not sufficient. React Router revalidates an *active* fetcher after a navigation, so a scope change (an Active ⇄ Deleted filter switch, a new cursor scope) can deliver a **newly-identified copy of the page last loaded** in the very render where the reset effect has just cleared `processed`. The stale page is then appended on top of the new first page and the cursor advances past everything in between — silently stranding the records in the skipped pages.
- **Where it stands.** Fixed in [`useDeletedGoalPagination`](../../app/modules/goals/GoalsCollection.tsx) (PX-04 follow-up), which now consumes only data it actually requested since the last reset. The **same shape remains** in the three older paginators it was modelled on: `useGoalPagination` (same file), `useNotePagination` ([`NotesCollection.tsx`](../../app/modules/notes/NotesCollection.tsx)) and `useProjectPagination` ([`ProjectsCollection.tsx`](../../app/modules/projects/ProjectsCollection.tsx)). Their exposure is lower — Notes and Projects reset on a lifecycle/state switch, which is exactly the trigger — but the defect is structurally identical and was simply never hit.
- **Why it was not swept here.** The PX-04 follow-up fixed the paginator it introduced. Refactoring three untouched collection surfaces in a bug-fix PR would have widened it well past its scope and past what its tests cover.
- **Desired future state.** One shared keyset-pagination hook the collections configure, rather than four near-identical copies — the same "shared over bespoke" move DS-04 made for Cards. Failing that, apply the request-scoped guard to the three remaining copies. Either way the rule to encode: **a page is consumed only if it was asked for since the current scope began.**
- **Resolved 2026-08-01 by UX-01, in the shape this entry asked for.** [`app/shared/load-more/useKeysetPagination.ts`](../../app/shared/load-more/useKeysetPagination.ts) is the ONE hook, and it encodes the rule verbatim: every `loadMore` stamps a monotonic request id, a scope change clears it, and a response is applied only while a request from the current scope is outstanding — so a revalidated copy of a previous scope's page can never be appended to a fresh first page.
  - **Every copy is gone.** The audit found the problem was wider than this entry recorded: **six** private copies existed, not four (`useAreaPagination`, `useGoalPagination`, `useDeletedGoalPagination`, `useNotePagination`, `useProjectPagination` and Assets' `usePagination`), and **two** collections had no accumulating paginator at all. All six now delegate to the shared hook.
  - **The two absences are closed too.** `/meetings` and `/reviews` paginated by NAVIGATING to the next page — replacing the list and discarding the owner's scroll position — and Meetings labelled that control "Load more", which is not what it did. Both now use the shared hook and the shared `LoadMore` affordance, so all eight collections behave identically.
  - **Notes' extra guard was subsumed, not dropped.** `useNotePagination` additionally discarded a page whose echoed `state` no longer matched the selected lifecycle view. The shared request-scoped rule is strictly stronger — it discards ANY response issued under a previous scope, not only one whose state field happens to disagree.
  - **Evidence.** [`test/unit/load-more/useKeysetPagination.test.tsx`](../../test/unit/load-more/useKeysetPagination.test.tsx) covers accumulation, boundary de-duplication, a retryable failed page that does not advance the cursor, and the exhausted no-op; [`e2e/ux-01-daily-driver.spec.ts`](../../e2e/ux-01-daily-driver.spec.ts) asserts neither collection offers a page-replacing link any more; the existing Projects/Goals/Areas/Notes/People/Assets "Load more" journeys pass unchanged.
- **Related roadmap item.** [UX-01](../roadmap/ROADMAP_V2.md#-ux-01--daily-driver-ux-ui-and-product-polish) (resolved here); [X-02](../roadmap/ROADMAP_V2.md#-x-02--saved-views--cross-module-filters) (where collection-wide list behaviour is next revisited); tracked alongside [DEBT-01](#-debt-01--duplicate-card-implementations-per-module--p2) as another per-module duplication of one idea.

### ☑ DEBT-49 — Two filter models coexist: DS-07 expressions and the Tasks declarative configuration — P3 — **RESOLVED 2026-08-08 (X-02)**
- **Current issue.** The product now contains two filter models. [DS-07](../design/DESIGN_SYSTEM.md#shared-filters-ds-07) is a client-side clause builder (`FilterExpression`: field → operator → value, evaluated in the browser over supplied records). TASKS-03 added a **declarative configuration** that names filter dimensions from closed sets and is translated to trusted predicates by the repository ([ADR-059](../decisions/ARCHITECTURE_DECISIONS.md#adr-059-the-tasks-collection-contract--one-declarative-view-configuration-server-side-filtering-and-grouping-and-saved-views-as-validated-configuration)).
- **Why both exist, honestly.** They answer different questions, and the second is not a fork of the first. A persisted `FilterExpression` could name a repository field, which makes storing one a persisted injection surface — so a saved, server-executed view could not have been built on DS-07 without weakening it. DS-07 remains correct for what it does; it is simply not a server-side query contract, and was never documented as one.
- **Impact.** Two things a future reader must tell apart, and a real risk that a third collection picks the wrong one. It is a comprehension and consistency cost, not a correctness one: neither model can produce the other's failure mode.
- **Desired future state.** ONE declarative, server-translatable configuration contract shared by every collection, with DS-07's clause builder retained (or retired) explicitly as the client-side evaluator it is. The Tasks contract is deliberately built to generalise — the config, its validation and its URL codec contain no Task-specific logic beyond the dimension names.
- **Closing condition.** At least one non-Tasks collection (Projects or Notes) is filtering through the shared declarative contract, the contract has moved out of `app/kernel/task-views` into a collection-agnostic home, and `DESIGN_SYSTEM.md` states which model a new collection should use in one sentence without qualification.
- **TASKS-04 mapping.** Intentionally retained. TASKS-04 may add Inbox/Unassigned/recurrence dimensions to the existing Task configuration, but it must not start the cross-module saved-view generalisation.
- **Resolved 2026-08-08 by [X-02](../roadmap/ROADMAP_V2_1.md#-x-02--saved-views--cross-module-filters), on exactly the closing condition written above.** The declarative configuration moved out of `app/kernel/task-views` into a collection-agnostic home (`app/kernel/views`) and now spans SIX entity types — Tasks, Projects, Goals, Notes, Meetings and Reviews — through the cross-module `/views` surface, so the "at least one non-Tasks collection" bar is cleared several times over. `~/kernel/task-views` became a thin façade: `TaskSavedView` and `TaskViewRepository` are the generic `SavedView<TaskViewConfig>` / `SavedViewRepository<TaskViewConfig>`, the error family is literally the same classes, and the Tasks module was not otherwise touched.
- **What happened to DS-07, stated without qualification.** DS-07's `FilterExpression` is the CLIENT-side clause builder for local/fixture collections, and it is retained as exactly that — the Activity feed and the design fixtures are its consumers. It has no persistence role and no server-query role, and X-02 gave it neither. The one sentence a new collection needs: **a collection that filters records in the browser uses DS-07; a collection whose filters are executed by a repository — and any collection with saved views — uses the declarative view configuration in `app/kernel/views`.** Recorded in [`DESIGN_SYSTEM.md → Filters`](../design/DESIGN_SYSTEM.md#shared-filters-ds-07) and [ADR-082](../decisions/ARCHITECTURE_DECISIONS.md#adr-082-one-saved-view-system-two-kinds--the-tasks-declarative-configuration-generalised-into-a-cross-module-query-contract).
- **No third model was introduced**, and the count went DOWN rather than up: one persisted, server-translated contract with two saved-view kinds, plus one client-side evaluator that was always a different thing.
- **Related roadmap item.** [X-02](../roadmap/ROADMAP_V2.md#-x-02--saved-views--cross-module-filters) ☑.

### ☑ DEBT-63 — "Load more" could silently drop a page — P1 — **RESOLVED 2026-08-01**

- **Filed as a test-timing curiosity. It was a product defect.** The first draft of this entry recorded two keyset-pagination component tests failing "only under heavy machine load", noted CI was green, and deliberately declined to widen their waits without a reproduction. Then the same family failed on CI on a dedicated runner (`NotesCollection.test.tsx`, run 30715617556), which falsified the "only under load" reading and forced a real diagnosis.
- **The diagnosis, and the experiment that settled it.** Reproduced locally at ~1 run in 12 by running the Notes and Projects collection suites together. The decisive step was widening the wait to **8 seconds**: it still failed. That rules out slowness — the page was never delivered at all. Tracing the shared hook then showed the mechanism exactly, and there were **two** independent drop paths:
  1. **The mount-time scope reset.** `useEffect` runs after paint, so a `findBy*` (which resolves during render) followed by a click could land *before* React flushed the mount effect. The reset then ran for the first time with a request already stamped, cleared `requested.current`, and the page that arrived was discarded as belonging to a previous scope.
  2. **The premature failure branch.** `fetcher.load()` does not synchronously leave the idle state, so `state === "idle" && data === undefined` has two meanings — "settled with nothing" and "has not started yet". The branch treated them alike, so it fired in the window between stamping the request and the fetcher going `loading`, set the retry state and cleared the request; the real page was then dropped.
- **What the owner saw.** Click "Load more"; the spinner clears; nothing is added; the cursor does not advance. A second click works. **All eight collections share this hook** (Areas, Goals, Notes, Projects, People, Assets, Meetings, Reviews), so it was product-wide.
- **The fix.** Reset only on a genuine scope CHANGE (compared by value, seeded with the mount scope) rather than whenever the effect happens to run; and gate the failure branch on a `started` flag that is only set once the fetcher has actually left idle. Neither weakens the DEBT-45 rule this hook exists to encode — a scope that genuinely changes still discards an in-flight request, which is exactly what must happen.
- **Measured before and after,** running the Notes + Projects collection suites together: **1 failure in 12** before; **5 in 30** with only the first fix (which is why both were needed, and how the second was found); **0 in 40** with both. The full unit suite then passed **3/3 consecutive runs (3128 tests)**.
- **Regression coverage, stated honestly.** The two collection suites that reproduced it are the guard: they exercise the path and went from intermittently red to 40/40 green. An attempt to add a dedicated repeated-journey test to `useKeysetPagination.test.tsx` was **removed rather than shipped** — it passed 5/5 against the *pre-fix* hook, so it guarded nothing, and a check that cannot fail is worse than no check because it reads as protection. The race only opens in the larger collection component trees, not in the isolated harness.
- **The lesson worth keeping.** `test/unit/load-more/useKeysetPagination.test.tsx` already carried a widened 5-second wait with a comment blaming "a fully-parallel suite run". That widening was masking this defect. **An intermittent test that is fixed by waiting longer has not been diagnosed** — the 8-second experiment is what turned a suspected flake into a found bug, and it cost one command.
- **Related roadmap item.** [UX-01](../roadmap/ROADMAP_V2.md#-ux-01--daily-driver-ux-ui-and-product-polish) (which introduced the shared hook); [DEBT-45 (pagination)](#-debt-45--keyset-paginators-can-consume-a-revalidated-fetcher-page-after-a-scope-reset--p3--resolved-2026-08-01), whose rule this preserves.

### ☐ DEBT-61 — An export is not a point-in-time snapshot, and a busy workspace can produce a slightly incoherent one — P3

- **Current issue.** [X-04](../roadmap/ROADMAP_V2.md#-x-04--export--data-portability) reads the workspace through a SEQUENCE of bounded statements. Each statement sees a consistent database, but the sequence does not: a write committed while the export is running is visible to the collections read after it and absent from those read before. A task created mid-export can therefore land in `entities` with no `taskDetails` row, or a link can name an entity that had not yet been read — which the snapshot validator would reject, failing the export rather than shipping an inconsistent file.
- **Why it was accepted.** D1 exposes no cross-statement snapshot for this read pattern through the Workers binding, so the alternatives were to claim a guarantee that does not exist, or to state the real one. X-04 states it — in `meta.consistency`, `manifest.json`, the archive `README.md` and the vault's `Export Information.md` — and mitigates it by reading collections **sequentially rather than concurrently**, which narrows the window. For a single-owner product where an export is a deliberate, occasional action, the practical exposure is close to zero: it requires a write to land in the second or so between two specific collection reads.
- **Desired future state.** If D1's Sessions API (or an equivalent read-snapshot mechanism) becomes usable from the Workers binding for a multi-statement read, bind the whole export to one snapshot and change `meta.consistency` to say so. Until then the honest statement is the correct behaviour, not a workaround.
- **Evidence.** [`build-snapshot.ts`](../../app/platform/export/build-snapshot.ts) (the sequential read and the reasoning), `SNAPSHOT_CONSISTENCY` in [`workspace-snapshot.ts`](../../app/kernel/export/workspace-snapshot.ts), and the validator's referential-integrity checks in [`snapshot-validation.ts`](../../app/kernel/export/snapshot-validation.ts).
- **Related roadmap item.** [SET-02](../roadmap/ROADMAP_V2.md#-set-02--backup--restore) — a scheduled backup runs unattended and hits this window more often than a hand-pressed export does, so it is the item that should decide whether the mitigation is still enough.

### ☐ DEBT-62 — The whole export is assembled in memory, so it is bounded rather than unbounded — P3

- **Desired future state.** A sign-out path DalyHub owns end to end: an in-app control that clears the offline database and DalyHub's caches BEFORE redirecting to the Access logout endpoint, plus a "clear offline data when I sign out" preference for anyone who wants it unconditional. This belongs with [SET-03](../roadmap/ROADMAP_V2_1.md#-set-03--account--security), which is already the owner-facing session/identity surface.
- **Closing condition.** Signing out through the DalyHub control leaves no `dalyhub-offline` database and no `dalyhub-*` cache on the device, proven by a Playwright assertion, with queued captures either synced first or explicitly confirmed as discarded.
- **Related roadmap item.** [SET-03](../roadmap/ROADMAP_V2_1.md#-set-03--account--security).

### ☐ DEBT-69 — Offline capture receipts accumulate with no prune — P3

- **Current issue.** `offline_capture_receipts` (migration `0027`) is written once per replayed offline capture and never deleted. Its purpose is to survive the retry window — minutes, not years — but nothing removes an old row. `created_at` is indexed for exactly this, and the table is bounded by how many captures the owner actually makes offline, so this is small and slow-growing rather than dangerous.

### ☐ DEBT-71 — A replayed capture whose Worker died mid-creation cannot be resolved automatically — P2

- **Current issue.** Offline capture replay claims an idempotency key in `offline_capture_receipts` *before* the module creates anything, and finishes the receipt with the created id afterwards. D1 has no interactive transaction that can span the module's own creation code, so a Worker that dies between those two writes leaves a receipt whose outcome is undecidable: the create may have committed just before the process ended, or never run at all. DalyHub retires the key rather than guessing (`capture-receipts.server.ts`), so no duplicate is ever created — but the owner is asked to check whether the capture arrived, and the queued capture is marked as needing attention rather than syncing.
- **Impact.** Rare (it needs a Worker to die inside a one-round-trip window) and never destructive: the capture's text stays on the device and nothing is duplicated. The debt is that a resolvable situation is handed to the owner.
- **Desired future state.** Make the creation itself idempotent so there is no second write to lose: derive the created record's primary key from the idempotency key, so replay is an `INSERT … ON CONFLICT DO NOTHING` against the record table and the receipt becomes an optimisation rather than the guarantee. That is a change to how the three modules mint ids, which is why it was not folded into the PWA milestone.
- **Closing condition.** A kernel test kills the request between create and receipt completion, replays the same key, and asserts exactly one record exists and the replay reports its id — with no owner-facing "check whether this arrived" message.
- **Related roadmap item.** [PWA/offline](../development/PWA_AND_OFFLINE.md#11-known-limitations) (follow-on).

### ☑ DEBT-81 — No application-level CSRF defence — P2 — RESOLVED 2026-08-05

- **Original issue.** [AUDIT-05] No `Origin`/`Sec-Fetch-Site`/`Referer` check existed on any mutation (`app/platform/request/request-boundary.ts:61` authenticated but did not check origin); no CSRF token was minted; there is no app session cookie — auth rides the Cloudflare Access `CF_Authorization` cookie whose SameSite is set by Cloudflare and asserted nowhere. ADR-016 reasoned only about token *forgery*, not session-riding CSRF.
- **Impact.** A compromised/XSS'd sibling subdomain of `daly.id.au` is same-site and could drive authenticated mutations; a future `SameSite=None` Access config would open plain cross-site CSRF.
- **Resolved (2026-08-05, AUDIT-FIX-04).** The absence was confirmed first: nothing in the request platform read either header. One canonical policy now runs ONCE at the shared boundary, so it covers every current and future mutation route without a single per-route check. `GET`/`HEAD`/`OPTIONS` are safe; everything else — including unknown and future methods, because the safe list is an allowlist — must carry an `Origin` that matches the request URL's own origin by exact scheme + hostname + effective port. There is no suffix match, no registrable-domain comparison and no wildcard subdomain, so **`same-site` is rejected as firmly as `cross-site`**: `https://other.daly.id.au` is same-*site* with `hub.daly.id.au` and is refused. `Sec-Fetch-Site` is read as corroboration only — `same-origin` or absent is accepted alongside an exact `Origin`, anything else is a rejection, and a hostile `Origin` claiming `Sec-Fetch-Site: same-origin` is rejected as inconsistent. **Missing `Origin` fails closed** even when `Sec-Fetch-Site: same-origin` is present: browsers attach `Origin` to every non-`GET`/`HEAD` request and DalyHub has no non-browser mutation client, so the compatibility case was deliberately not taken. The trusted origin is `new URL(request.url).origin` — authoritative because production disables `workers_dev`/`preview_urls`, so only the Access-protected custom domain routes here; no configuration value, no secret and no forwarding header (`X-Forwarded-Host`/`X-Forwarded-Proto`) is consulted. Ordering: authenticate → establish session → check provenance → reject, so a rejected mutation never provisions membership, never invokes React Router, never touches a repository, never records Activity and never mutates data; an unauthenticated request keeps its existing 401/403/503. The rejection is a generic `403 Request rejected.` with the baseline security headers, `private, no-store`, no reflected origin, no reason code, no CORS header and no redirect. `/health` keeps its exact-path public bypass for safe methods only. Offline replay is unaffected: it posts to the ordinary create routes with a plain same-origin `fetch`, so the browser supplies the provenance, and a 403 is classified `blocked` (not retried indefinitely). No migration, no token table, no cookie, no third-party dependency.
- **Evidence.** Source: [`app/platform/request/mutation-provenance.ts`](../../app/platform/request/mutation-provenance.ts) (the pure policy), [`request-boundary.ts`](../../app/platform/request/request-boundary.ts) (ordering + public-path method restriction), [`security-headers.ts`](../../app/platform/request/security-headers.ts) (`buildCrossOriginRejectionResponse`). Tests: 47 policy cases in [`test/unit/request/mutation-provenance.test.ts`](../../test/unit/request/mutation-provenance.test.ts); the eight boundary proofs in [`test/unit/request/request-boundary.test.ts`](../../test/unit/request/request-boundary.test.ts); real-runtime/real-D1 proof that a rejected mutation leaves no Task, no Activity and no membership row in [`test/kernel/request-boundary-csrf.test.ts`](../../test/kernel/request-boundary-csrf.test.ts); a real second local origin driving a genuine browser-generated `Origin` in [`e2e/csrf.spec.ts`](../../e2e/csrf.spec.ts); replay provenance in [`test/unit/pwa/offline-sync.test.ts`](../../test/unit/pwa/offline-sync.test.ts).
- **Related finding.** [AUDIT-05](END_TO_END_AUDIT_2026_08_05.md#audit-05--no-application-level-csrf-defence--p2). **Related roadmap item.** [AUDIT-FIX-04](../roadmap/ROADMAP_V2_1.md#-audit-fix-04--csrf-defence-in-depth--react-router-bump-p2p3).

### ☑ DEBT-82 — Multi-device preference lost-update; `version` never enforced — P3 — RESOLVED 2026-08-08

- **Original issue.** [AUDIT-07] `d1-app-preferences-repository.ts` `update` read the whole record, merged the caller's fields into that read, and upserted **every** column from the merged snapshot; `version = version + 1` was bookkeeping only — nothing compared it. Two devices saving different settings from reads of the same version each wrote the other's field back to its stale value, and both calls reported success. Confirmed on `main` before the fix and reproduced as the first test in the regression suite below.
- **Resolved (2026-08-08, AUDIT-FIX-06).** The write is now a **patch**, not a snapshot replacement: the statement's `DO UPDATE SET` names only the columns present in the validated patch, and its change predicate and version guard are evaluated **inside** that one statement, so nothing can be written between a check and the write. Two consequences, chosen deliberately because preferences are two different shapes of value:
  - **Independent fields merge.** A device saving `timezone` cannot touch `appearance`, so the common two-device case has no conflict to resolve and the owner is never asked about a disagreement that does not exist. This is the same per-column shape `updateTask` already used.
  - **A DERIVED value gets a real precondition.** The navigation hidden-set is read-modify-write (read the set, add an id, write the whole set) and therefore cannot merge by column. `update` accepts `options.expectedVersion`; supplying it appends `AND owner_app_preferences.version = ?` to the write, and a stale write matches zero rows and raises the new typed `AppPreferencesConflictError` instead of reporting success. **`version` is therefore no longer incremented-and-ignored** — it is the write precondition on the one path whose value is derived from the old one.
  - The Settings `toggle-navigation` action quotes the version it read and re-derives from the newer set on a conflict (bounded to 3 attempts), so the owner's toggle is never lost, never overwrites another device's toggle, and neither device is asked to resolve anything. A conflict that survives the retries answers **`409`**, never a `500`.
- **Also fixed on the way.** `parseTimezone` rejected `UTC` — `Intl.supportedValuesOf('timeZone')` lists canonical zones only and omits links — while the Settings picker offered it, so choosing UTC failed validation on save. The validator now falls through to the runtime probe, which is what every owner-calendar helper actually uses.
- **Evidence.** Source: [`d1-app-preferences-repository.ts`](../../app/platform/storage/d1/d1-app-preferences-repository.ts), [`app-preferences.ts`](../../app/kernel/preferences/app-preferences.ts) (`UpdateAppPreferencesOptions`), [`app-preferences-errors.ts`](../../app/kernel/preferences/app-preferences-errors.ts) (`AppPreferencesConflictError`), [`settings/routes/index.tsx`](../../app/modules/settings/routes/index.tsx) (`withPreferenceRetry`, the `409`). Tests: 10 real-D1 cases in [`test/kernel/app-preferences-concurrency.test.ts`](../../test/kernel/app-preferences-concurrency.test.ts) — two stale devices keep BOTH changes, untouched columns are byte-identical, a same-field race resolves to the later write with the version advancing once per change, a stale compare-and-set is refused with the newer data intact, version 0 means "no row yet", an unchanged write is an idempotent no-op rather than a conflict, and a concurrency token from one workspace cannot authorise a write in another.
- **Remaining limitation.** Two devices changing the SAME scalar setting still resolve to the later write. That is the only honest answer for one field with two intentions, and nothing else is lost with it; the entry does not claim otherwise.
- **Related finding.** [AUDIT-07](END_TO_END_AUDIT_2026_08_05.md#audit-07--multi-device-preference-lost-update--p3). **Related roadmap item.** [AUDIT-FIX-06](../roadmap/ROADMAP_V2_1.md#-audit-fix-06--concurrency-and-one-owner-day-p3).

### ☑ DEBT-83 — Concurrent note-content saves are blind last-write-wins — P3 — RESOLVED 2026-08-08

- **Original issue.** [AUDIT-08] `d1-note-details-repository.ts` overwrote the whole content guarded only against *identical* content; there was no base-version precondition, so two tabs or devices editing one note silently lost one side's writing. Extends [DEBT-47](#-debt-47--an-open-autosave-editor-does-not-adopt-a-server-side-change-to-its-field--p2) from "does not adopt a change" to "destroys one". Offline note *editing* is not shipped (PWA-02 deferred), so the trigger was concurrent online editing.
- **Resolved (2026-08-08, AUDIT-FIX-06).** `NoteDetailsRepository.update` accepts `options.expectedContentUpdatedAt` — the content version the editor loaded — and folds it into the SAME upsert as a compare-and-set, so the check cannot be raced. A stale save matches zero rows and is reported as the typed `NoteDetailsConflictError`; the route answers **`409`** carrying the newer stored text, never a `500` and never a false success. `null` is a distinct quoted value meaning "this note had no saved content when I opened it", guarded as "the stored content is still empty" so a `setTags`/`setArchived` row creation cannot manufacture a false conflict. Callers that quote nothing (the capture panel writing a brand-new note's first body) keep the previous behaviour exactly, but a caller that quotes an UNPARSEABLE value is refused with `400` and writes nothing — degrading that to "no precondition" would have left a stale client an opt-out from the compare-and-set, and refusing costs the owner nothing because their draft never left the editor.
- **The editor's answer reuses the ONE existing reconciliation UI.** No Notes-only dialog and no automatic Markdown merge. A refusal is fed into the shared DS-06 coordinator through a new, honest third save outcome — `{ outcome: "conflict" }`, which is neither success (nothing was written) nor error (nothing malfunctioned) — so the draft stays in the editor, the status returns to `unsaved` rather than `error`, and the newer server text is OFFERED through the same [`RemoteChangeBanner`](../../app/shared/forms/RemoteChangeBanner.tsx) an out-of-band change already uses: *load the newer version*, or *keep mine*. - **Closing condition (met).** Kernel tests assert a stale content save is refused, not silently applied, and that the newer stored content is intact afterwards.
- **Related finding.** [AUDIT-08](END_TO_END_AUDIT_2026_08_05.md#audit-08--concurrent-note-content-saves-are-blind-last-write-wins--p3). **Related roadmap item.** [AUDIT-FIX-06](../roadmap/ROADMAP_V2_1.md#-audit-fix-06--concurrency-and-one-owner-day-p3); [DEBT-47](#-debt-47--an-open-autosave-editor-does-not-adopt-a-server-side-change-to-its-field--p2).

- **Resolved (2026-08-08, with SET-02).** The dump is now encrypted **on the runner, before it becomes an artifact**, with GnuPG symmetric AES-256 and explicitly stated S2K parameters (`--s2k-mode 3`, `--s2k-digest-algo SHA512`, `--s2k-count 65011712`). One pipeline, `scripts/production-backup.mjs`, serves the scheduled and the manually dispatched run identically — there is no weaker manual path.
- **What GitHub now stores.** `dalyhub-v2-production-<stamp>.sql.gpg` and a `metadata.json` of sizes, SHA-256 digests, run identity and the decrypt command. **No plaintext dump. No key.** The plaintext exists only in a scratch directory removed by a trap that runs even on failure, and a guard step refuses the upload if the artifact directory contains anything unencrypted or the metadata names a credential-shaped field.
- **The key.** `BACKUP_ENCRYPTION_PASSPHRASE`, in the protected `production` GitHub environment. It is read from a file written under `umask 077`, never from `argv` and never interpolated into a shell string; shell tracing is never enabled and no log line carries backup contents. It is not committed, not documented, not uploaded and not printed. The owner holds a copy **off GitHub**; rotation, and what happens to older backups, are documented in [`BACKUP_AND_RESTORE.md` §6](../development/BACKUP_AND_RESTORE.md#6-the-recovery-key).
- **Recoverability is proved, not asserted.** Every run decrypts its own artifact back, compares SHA-256 with the original and asserts the plaintext does not appear in the ciphertext. `test/unit/deploy/production-backup-encryption.test.ts` does the same end to end with a real dump, a throwaway key and the real `gpg` invocation: encrypt → prove the sensitive strings are absent → decrypt → byte-identical → still passes structural validation; a wrong key fails; a tampered ciphertext fails. `test/unit/deploy/production-backup-workflow.test.ts` holds the workflow contract — upload contents, cleanup, no secret on a command line, the pre-export key guard, minimal permissions, `schedule`/`workflow_dispatch` only (no pull request can run it), and the deliberate retention.
- **Retention.** Unchanged at 30 days, and the reasoning is recorded beside the value: it was not reduced (encryption addressed the exposure) and not extended (encryption is not a reason to keep more data on GitHub for longer).
- **Related finding.** [AUDIT-11](END_TO_END_AUDIT_2026_08_05.md#audit-11--production-d1-dump-stored-as-a-github-artifact--p2p3). **Related roadmap item.** [SET-02](../roadmap/ROADMAP_V2_1.md#-set-02--backup--restore-v21).

### ☑ DEBT-87 — Non-atomic cross-repository flows can leave inconsistent state — P3 — **RESOLVED 2026-08-08**

- **Original issue.** [AUDIT-13] Meeting item→task conversion (`app/platform/meetings/follow-up-operations.ts`) and obligation→task completion (`d1-asset-history-repository.ts`, task completed in a separate transaction *before* the obligation batch) span two writes; a mid-way failure leaves an orphan Task, or a completed Task against a still-open obligation. Documented in the code, untested.
- **Resolved (2026-08-08, AUDIT-FIX-07).** Both are now ONE `D1Database.batch()`.
  - **Meeting item → Task** was five transactions with a compensating `spine.softDelete`. The compensation covered a *thrown* failure and could not cover the process not being there to run it, which is exactly the orphan the finding described. The conversion is now one transaction assembled from the Task, Meeting and EntityLink adapters' OWN prepared statements — no repository's SQL is re-authored — behind ONE domain operation, `MeetingTaskConversionRepository.convert`. A failure now leaves **no row at all**, not a soft-deleted one, so a retry is a first attempt. Idempotency is the `meeting_item_tasks (workspace_id, item_id)` unique index: a losing concurrent conversion rolls its whole transaction back and returns the winner's Task.
  - **Obligation → Task completion** closed the Task first. The Task's completion statements now join the obligation's own batch behind the `completionGuard` the obligation already used, evaluated *inside* the transaction, so the Task closes only if the obligation actually closed and any later failure rolls both back. The `catch { taskOutcome = "already_closed" }` that recorded every Task failure as an established fact in the Activity payload is gone: `taskOutcome` is derived from a real pre-read and names what the same transaction did.
  - **The APIs that permitted the old sequences are deleted**, not deprecated: `MeetingRepository.linkFollowUpTask` and `ObligationTaskGateway.completeTask`. Each was atomic on its own and useless as a guarantee, because the thing it recorded had been created by a different transaction.
  - `createTask` now accepts `status` and `description`, removing two further transactions rather than moving them.
- **Evidence.** 17 real-Workers/real-D1 cases in [`test/kernel/audit-13-atomic-operations.test.ts`](../../test/kernel/audit-13-atomic-operations.test.ts): success commits everything; a fault on EITHER side of each operation commits nothing (counted against **every** Task row, including soft-deleted ones, so "rolled back" is distinguishable from "compensated"); a retry after a failure yields exactly one Task, one mapping, one link and one event; concurrent requests cannot contradict each other; another workspace can neither convert nor complete; and the obligation event's `taskOutcome` matches committed state in all three cases. Plus rewritten fault-injection cases in [`meeting-follow-up.test.ts`](../../test/kernel/meeting-follow-up.test.ts) and a browser journey ([`e2e/audit-13-conversion-atomicity.spec.ts`](../../e2e/audit-13-conversion-atomicity.spec.ts)) proving a double-submitted, replayed and refused conversion each behave.
- **Remaining limitation, and one adjacent class left open.** Two things, both stated rather than hidden.

  **(a) Flows of the same shape that AUDIT-13 did not name are untouched**, because the finding is the finding: quick capture with a context (`createTask` + `applyCaptureRelationship`, compensating) and creating a Task for an obligation (`createTask` + `linkObligationTask` + `entityLinks.create`) are still compensating sagas with the same residual window. The AI acceptance paths' `createTask` + `updateTask({description})` pairs WERE folded in, since `createTask` now takes a description — that makes accepting an unsourced Task atomic outright. Making the remaining two atomic is [ADR-083](../decisions/ARCHITECTURE_DECISIONS.md#adr-083-a-compound-domain-mutation-is-one-storage-transaction-composed-from-the-owning-repositories-statements)'s technique applied to two more flows, which is follow-up work and not a rider on an atomicity PR. Traced in [`DOC_EDITOR_ATOMIC_AUDIT_2026_08_08.md` §3.3](DOC_EDITOR_ATOMIC_AUDIT_2026_08_08.md).

  **(b)** ONE write stays outside the conversion's transaction: the AI acceptance path's `addItem`. Recording an action the owner approved is a legitimate change to the Meeting in its own right, `addItem` is atomic with its own ordinal-conflict retry, and an action item without a Task is a state the Meetings module already models and shows. A failed conversion after it leaves the action visible and no Task, and a retry REUSES that item rather than adding a second — no duplicate, nothing lost.
- **Related finding.** [AUDIT-13](END_TO_END_AUDIT_2026_08_05.md#audit-13--non-atomic-cross-repository-flows--p3). **Related roadmap item.** [AUDIT-FIX-07](../roadmap/ROADMAP_V2_1.md#-audit-fix-07--atomic-compound-mutations-one-long-form-editor-and-the-dead-code-p3--delivered-2026-08-08). **ADR.** [ADR-083](../decisions/ARCHITECTURE_DECISIONS.md#adr-083-a-compound-domain-mutation-is-one-storage-transaction-composed-from-the-owning-repositories-statements).

### ☐ DEBT-95 — `AGENTS.md` §6 and §15 still describe the appearance the product no longer has — P2
- **Current issue.** [ADR-075](../decisions/ARCHITECTURE_DECISIONS.md#adr-075-the-appearance-preference-and-one-authority-for-routine-creation) gave the owner a three-value **Appearance** preference over the one generated light/dark pair. Two statements in the constitution were written for the world before it and are now false as written: §6 says the pair is "selected by the operating system", and §15 says "`prefers-color-scheme` is not merely honoured — it is the *only* thing that decides light or dark, because there is no theme preference to override it". §15 is the worse of the two, because it sits inside the accessibility requirements, which is the last place a reader should have to discount what they read.
- **Impact.** An agent reading the constitution — which §0 makes the highest authority — is told the product cannot do something it demonstrably does. The correct reading requires also knowing that ADR-075 supersedes it, which is exactly the indirection §0's supersession clause is meant to be a stopgap for, not a resting state.
- **Desired future state.** §6 states that there is one pair and no theme feature, and that the owner chooses **System / Light / Dark** over it. §15 keeps its requirement — honour the device — and says plainly that `System` is the default and is that honouring, while an explicit Light or Dark is a deliberate user override, which is user control rather than a failure to respect a device signal.
- **Closing condition.** A dedicated PR amending `AGENTS.md`, per the file's own closing rule ("change this file in a dedicated PR that explains the reasoning"). ADR-075's supersession table is then redundant and can say so.
- **Related roadmap item.** None — this is documentation owed by the shell-polish change, deliberately deferred so a constitutional amendment is not folded into a feature PR.
