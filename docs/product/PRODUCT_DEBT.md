# PRODUCT_DEBT.md — Known Inconsistencies & Target States

> The register of **known product/UX inconsistencies** — where the product diverges from the [Design System](../design/DESIGN_SYSTEM.md), the [architecture rules](../../AGENTS.md#9-architecture-philosophy), or the [product principles](PRODUCT_PRINCIPLES.md) — and the target state for each.
>
> **Context.** DalyHub V2 is a redevelopment of a prompt-driven V1. Much of the debt below is *inherited* from V1's patterns and is precisely what the V2 [roadmap](../roadmap/ROADMAP_V2.md) exists to resolve. As V2 is built greenfield on the shared foundation, resolving an item usually means "build the shared pattern instead of the legacy one." New debt discovered during V2 work is logged here too.

---

## How to use this register

- **Every entry links to a [ROADMAP_V2](../roadmap/ROADMAP_V2.md) item** that resolves it. Debt without a roadmap home is a signal the roadmap is incomplete — add the item.
- **When you touch code carrying debt,** either resolve it (and check the box) or update the entry with what you learned ([campsite rule](../../AGENTS.md#12-development-workflow)).
- **Found new debt?** Add it with the [template](#entry-template) rather than leaving it undocumented. Undocumented divergence is the worst kind.
- **Priority:** `P1` (actively harms coherence/trust), `P2` (notable friction), `P3` (cleanup).
- **Status:** ☐ open · ◐ in progress · ☑ resolved.
- **IDs are unique and stable.** Never reuse a retired number; never issue a number twice. The next free ID is **DEBT-77**. (One entry, **AUDIT-IDENTITY-01**, keeps its original audit identifier rather than being renumbered, so it stays traceable to the audit that raised it.)
  - **Known ID collision, recorded rather than silently renumbered (UX-01, 2026-08-01).** The number **DEBT-45** was issued twice: once for *"A captured record is not linked to the context it was captured from"* and once for *"Keyset paginators can consume a revalidated fetcher page after a scope reset"*. Renumbering either would break every existing cross-reference, so both keep the number and each is identified by its title. The pagination one is now ☑; the capture-context one remains ◐. Do not issue DEBT-45 again.
- **Close only on evidence.** An entry moves to ☑ when the source code *and* its tests prove it, cited in the entry. "It should be fixed by now" is not evidence.

### ◐ DEBT-01 — Duplicate card implementations per module — P2
> **P1 → P2 (V2 release closure, 2026-08-01).** The shared DS-04 Card is what every
> collection composes; UX-01 retired the last bespoke collection card (Meetings).
> What remains is ONE deliberate, documented exception — the Diary timeline node,
> split out as [DEBT-46](#-debt-46--diarys-timeline-node-is-still-not-the-shared-card--p3-deliberately-downgraded).
> An accepted exception with a stated reason is friction, not a coherence failure.
> **Target release:** V2.1 or later, with DEBT-46.

- **Partly resolved by UX-01 (2026-07-28).** Meetings no longer uses the bespoke
  `dh-meeting-card` collection; `/meetings` now composes `CollectionLayout`,
  `CardCollection` and the shared DS-04 `Card` with bounded search/sort/pagination.
  Diary's timeline treatment and any remaining specialised cards keep this debt
  open until audited separately.
- **Current issue.** V1 grew a bespoke card per module; the same entity looks and behaves differently in different places.
- **Desired future state.** One configurable shared [Card](../design/DESIGN_SYSTEM.md#cards); every entity renders through it.
- **Progress (2026-07-27 audit).** [DS-04](../roadmap/ROADMAP_V2.md#-ds-04--shared-cards) shipped the one entity-agnostic Card ([`app/shared/card`](../../app/shared/card)) and Areas, Assets, Goals, Notes, People, Projects, Reviews, Tasks and Today all render through it. **Two V2 forks remain:** the Diary timeline node is a hand-rolled `dh-diary-entry` element ([`app/modules/diary`](../../app/modules/diary)) and the Meetings collection renders a hand-rolled `dh-meeting-card` anchor ([`MeetingsCollection.tsx`](../../app/modules/meetings/MeetingsCollection.tsx)) — neither imports `~/shared/card`, so neither inherits selection, quick actions, density, swipe or the shared a11y behaviour. Kept ◐ rather than resolved: the shared Card exists and is dominant, but the product is not yet card-uniform.
- **Update 2026-07-28 (PX-06).** The **Diary timeline node stays a deliberate, documented fork** rather than being forced into a Card variant. It is the strongest scanning surface in the product (subtype icon + badge + timestamp on a chronological spine), and every variant shape considered lost some of that for no user-visible gain — so PX-06 preserved the visual exactly and instead pulled Diary onto the shared pieces that *do* fit: the shared subtype-icon registry, the shared overflow menu and lifecycle, the shared create-label convention and one primary entry point per viewport. Meetings' bespoke settings section was retired onto the shared DS-10b surface in the same change. This entry stays ◐ for the Diary card itself, now as an **accepted exception with a stated reason** rather than an untracked divergence.
- **Related roadmap item.** [DS-04](../roadmap/ROADMAP_V2.md#-ds-04--shared-cards) (the shared Card) and [PX-06](../roadmap/ROADMAP_V2.md#-px-06--cross-module-polish--copy-convention) (retiring the Diary/Meetings forks); tracked alongside [DEBT-31](#-debt-31--cross-module-presentation-drift-todaydiary-forks-terminology-and-capitalisation--p2--presentation-half-resolved-2026-07-28).

### ☑ DEBT-03 — Multiple save patterns (autosave vs. explicit vs. modal) — P1
- **Current issue.** Different forms save differently; users can't predict whether edits persist. Erodes [trust](PRODUCT_PRINCIPLES.md#how-users-should-feel).
- **Desired future state.** One [Forms](../design/DESIGN_SYSTEM.md#forms) system with a predictable save model per field type.
- **Resolution.** [DS-06](../roadmap/ROADMAP_V2.md#-ds-06--shared-forms--field-controls) delivers ONE shared [forms system](../design/DESIGN_SYSTEM.md#shared-forms--field-controls-ds-06) in which the save mode is a **declared, visible part of the component contract**, never inferred: `useForm` for explicit Save/Cancel (dirty tracking, duplicate-submit prevention, draft preservation on failure, unsaved-navigation interception) and `useAutosaveField` for calm, deterministic autosave (`Unsaved`/`Saving`/`Saved`/`Couldn’t save`, stale-response-safe, retry). No modal-save pattern is introduced. The predictable model now exists design-system-wide; each product create/edit surface simply adopts it (there are no product forms today that still diverge).
- **Related roadmap item.** [DS-06](../roadmap/ROADMAP_V2.md#-ds-06--shared-forms--field-controls).

### ◐ DEBT-07 — Fragmented activity/history — P2
- **Current issue.** History (where it exists) is per-module and inconsistent; no unified timeline or audit trail.
- **Desired future state.** One [shared Activity model](../decisions/ARCHITECTURE_DECISIONS.md#adr-005-shared-activity-model) rendered as Timeline/Activity Feed everywhere.
- **Progress.** FND-05 + DS-05 established the one event model and the one renderer, and Tasks, Areas, Goals, Projects, Meetings, Assets and People each adopted it rather than forking a per-module history. [PEOPLE-02](../roadmap/ROADMAP_V2.md#-people-02--relationship-timeline) is the first surface to prove the harder half — a **unified, cross-record** history — without fragmenting anything: the Person Timeline reads the ONE Activity stream across the Person AND their linked records, through an additive kernel multi-anchor read, with cross-module event labels taken from the FND-06 module registry. No second timeline, relationship-event store or copied content was introduced, and [ADR-052](../decisions/ARCHITECTURE_DECISIONS.md#adr-052-the-unified-people-relationship-timeline--a-derived-multi-anchor-projection-over-the-one-activity-stream) records the pattern any future cross-record history should reuse. **[MEET-03](../roadmap/ROADMAP_V2.md#-meet-03--people--history-integration) (2026-07-28) is the first real test of that seam, and it held.** Meetings contributed genuine interaction history to the Person timeline through ONE manifest line and a multi-subject `meeting.held` event — no Meetings tab on the Person record, no interactions table, no `lastContactAt` column, no copied meeting summaries, and no People-module change at all (asserted by an architectural test). It also **removed** a small fragmentation the audit had not caught: the Person timeline was hand-rolling a Task-only entity destination, so linked Notes, Assets, Meetings and Reviews rendered as inert text; every reference now resolves through the ONE shared `entityDestination` helper. See [ADR-055](../decisions/ARCHITECTURE_DECISIONS.md#adr-055-a-meetings-occurrence-is-a-durable-write-once-fact-and-attendee-history-is-one-multi-subject-activity-event). **Still open:** modules that render no Timeline at all; the workspace-wide Activity Feed has no product surface yet (only the dev fixture); and the seven other module Activity routes still carry the same hand-rolled Task-only destination the People route just shed — each is a one-line change to the shared helper, deliberately left out of MEET-03's scope rather than bundled into it.
- **Related roadmap item.** [FND-05](../roadmap/ROADMAP_V2.md#-fnd-05--shared-activity-model) + [DS-05](../roadmap/ROADMAP_V2.md#-ds-05--shared-timeline--activity-feed) + [PEOPLE-02](../roadmap/ROADMAP_V2.md#-people-02--relationship-timeline) + [MEET-03](../roadmap/ROADMAP_V2.md#-meet-03--people--history-integration).

### ☑ DEBT-39 — `[[Wiki Links]]` create no EntityLink, and the resolver scans the whole workspace — P2
- **Current issue.** REL-01's wiki links are resolved at **navigation** time: [`wikilinks.ts`](../../app/platform/markdown/wikilinks.ts) rewrites `[[Title]]` to `/notes/resolve?title=…` and [`notes/routes/resolve.tsx`](../../app/modules/notes/routes/resolve.tsx) finds a matching entity and redirects.   2. **The resolver is an unbounded read.** It pages through **every** entity in the workspace with a deliberate "no page cutoff" (documented in the route), stopping early only on a note match. That is a correct-but-unbounded scan on a hot navigation path, contrary to the [performance expectations](../../AGENTS.md#16-performance-expectations) every other read honours with bounded, cursor-paginated queries.
- **Resolved (2026-07-28, NOTES-02).** The decision this entry asked for was made and recorded as [ADR-054](../decisions/ARCHITECTURE_DECISIONS.md#adr-054-note-knowledge--a-wiki-link-is-a-persisted-reference-and-knowledge-relationships-stay-entitylinks): **a wiki link in a saved note is a persisted reference.** Both halves are closed.
  1. **A relationship is now written.** `reconcileNoteReferences` ([`note-references.ts`](../../app/platform/entity-links/note-references.ts)) makes the note's typed `note.references` EntityLinks exactly match the `[[…]]` in its body on every content save, so a referenced record shows the reference in its Backlinks and both records' Timelines carry the kernel's `entity_link.*` events. Titles are matched ONCE, at save time, and the relationship is persisted by **stable id** — renaming the target keeps it, which is why "no fragile title-based matching" and "renaming does not break links" are both true. Duplicates collapse to one row; a reference inside code is never a relationship; removing the last mention unlinks; re-adding restores the SAME link id rather than duplicating. Reconciliation only ever touches `note.references` links whose SOURCE is that note, so nothing a user created by hand is disturbed, and it never fails the save (the Markdown source is the canonical record).
  2. **The unbounded read is gone.** Title resolution is `NoteQueryRepository.resolveReferenceTargets` — ONE bounded, chunked, indexed `lower(title) IN (…)` query with a total, stable tie-break (a Note wins, then the earliest-created record) — instead of paging every entity in the workspace with no cutoff.

### ☑ DEBT-42 — Repository-backed searches can fail the whole query on a long user input — P2
- **Current issue.** D1 caps a `LIKE` pattern at **50 bytes**; a longer pattern fails the ENTIRE statement with `LIKE or GLOB pattern too complex: SQLITE_ERROR`, not just that predicate. Every repository-backed search builds its pattern as `%<user input>%`, so **any query over ~48 characters — a pasted title, a copied sentence — returns a 500 rather than results.** Found empirically while building the Notes search (a full note title as the query, reproduced end to end), not by inspection. Truncation must never leave a trailing unpaired escape character, which SQLite rejects in its own right.
- **Related roadmap item.** [X-01](../roadmap/ROADMAP_V2.md#-x-01--global-search-maturity); [DS-08](../roadmap/ROADMAP_V2.md#-ds-08--shared-search).

  [`app/platform/storage/d1/like-pattern.ts`](../../app/platform/storage/d1/like-pattern.ts)
  and reused it across repository-backed Search projections, including the new
  Areas/Goals/Projects/Diary projections and the widened Tasks projection. The
  helper escapes `%`, `_` and `\`, bounds by UTF-8 bytes under D1's 50-byte pattern

### ☐ DEBT-44 — A held meeting appears on the timeline of a linked NON-attendee — P2
- **Current issue.** [MEET-03](../roadmap/ROADMAP_V2.md#-meet-03--people--history-integration)'s `meeting.held` names the Meeting as an Activity subject (so the Meeting's own Timeline carries it, and the Person timeline can link back to the canonical record). But a Person who is linked to that Meeting — by a `link.related`, or as an attendee added AFTER it was marked held — has the Meeting in their PEOPLE-02 anchor set, and `listForEntities` returns every event naming an anchor. So they see the line `Someone · Meeting held — <meeting>` on their relationship history even though their id is **absent** from the recorded attendee subjects.
- **Verified, not assumed (2026-07-28).** Raised by automated review on [#81](https://github.com/acedaly/DalyHub-V2/pull/81) and reproduced with a throwaway integration test against the real loader before being accepted: both a late-linked attendee and a `link.related` bystander receive the event, and the item's `subjects` array contains only the Meeting (`isAnchor: false`) — no Person.
- **Impact, stated honestly.** It is the PEOPLE-02 anchor contract working exactly as designed: a linked record's own events appear on your timeline, and `meeting.created` / `meeting.updated` already behave this way. The line is a true statement about the Meeting and disappears if you unlink. **But** "Meeting held" reads as *"we met"* in a way that "Meeting created" does not, so on a relationship history it is true-but-misleading for someone who was never an attendee — and it sits awkwardly beside MEET-03's own documented rule that a late-added attendee is "not retroactively added".
- **What is NOT affected.** The durable, Person-scoped fact is subject membership, and the [PEOPLE-03](../roadmap/ROADMAP_V2.md#-people-03--stay-in-touch-signals) contact seam reads `activity.listForEntity(personId)`, which returns only events naming that Person. So a non-attendee can never become a "last meaningful contact" through this. The defect is presentational, not a corruption of the contact signal.
- **Why it was not fixed in MEET-03.** The suggested remedy — filter `meeting.held` on the People read path — would put Meetings knowledge inside the People module, which MEET-03 explicitly forbids and which an architectural test asserts against. The architecturally clean fix is a **generic** People-timeline rule ("an event that names Person subjects appears on a Person's timeline only if that Person is one of them"), which carries no Meetings knowledge but **changes PEOPLE-02 semantics for every module's events** — e.g. a third party's `entity_link.created` would stop appearing. That is its own roadmap item, not a late addition to a shipped one (AGENTS.md §13, one item per PR).
- **Desired future state.** Decide the rule deliberately as part of [PEOPLE-03](../roadmap/ROADMAP_V2.md#-people-03--stay-in-touch-signals) or a dedicated PEOPLE item: either adopt the generic subject-membership rule (with tests and a documented PEOPLE-02 semantic change), or accept the anchor contract and make the distinction legible in the UI.
- **Related roadmap item.** [MEET-03](../roadmap/ROADMAP_V2.md#-meet-03--people--history-integration); [PEOPLE-02](../roadmap/ROADMAP_V2.md#-people-02--relationship-timeline); [PEOPLE-03](../roadmap/ROADMAP_V2.md#-people-03--stay-in-touch-signals).

### ☑ DEBT-45 — Keyset paginators can consume a revalidated fetcher page after a scope reset — P3 — **RESOLVED 2026-08-01**
- **Current issue.** Every "Load more" collection paginator follows the same shape: a `useFetcher`, an `appended` accumulator, and a `processed` ref that de-dupes by **object identity** so one response is applied once. Identity alone is not sufficient. React Router revalidates an *active* fetcher after a navigation, so a scope change (an Active ⇄ Deleted filter switch, a new cursor scope) can deliver a **newly-identified copy of the page last loaded** in the very render where the reset effect has just cleared `processed`. The stale page is then appended on top of the new first page and the cursor advances past everything in between — silently stranding the records in the skipped pages.
- **Where it stands.** Fixed in [`useDeletedGoalPagination`](../../app/modules/goals/GoalsCollection.tsx) (PX-04 follow-up), which now consumes only data it actually requested since the last reset. The **same shape remains** in the three older paginators it was modelled on: `useGoalPagination` (same file), `useNotePagination` ([`NotesCollection.tsx`](../../app/modules/notes/NotesCollection.tsx)) and `useProjectPagination` ([`ProjectsCollection.tsx`](../../app/modules/projects/ProjectsCollection.tsx)). Their exposure is lower — Notes and Projects reset on a lifecycle/state switch, which is exactly the trigger — but the defect is structurally identical and was simply never hit.
- **Why it was not swept here.** The PX-04 follow-up fixed the paginator it introduced. Refactoring three untouched collection surfaces in a bug-fix PR would have widened it well past its scope and past what its tests cover.
- **Desired future state.** One shared keyset-pagination hook the collections configure, rather than four near-identical copies — the same "shared over bespoke" move DS-04 made for Cards. Failing that, apply the request-scoped guard to the three remaining copies. Either way the rule to encode: **a page is consumed only if it was asked for since the current scope began.**
- **Resolved 2026-08-01 by UX-01, in the shape this entry asked for.** [`app/shared/load-more/useKeysetPagination.ts`](../../app/shared/load-more/useKeysetPagination.ts) is the ONE hook, and it encodes the rule verbatim: every `loadMore` stamps a monotonic request id, a scope change clears it, and a response is applied only while a request from the current scope is outstanding — so a revalidated copy of a previous scope's page can never be appended to a fresh first page.
  - **Every copy is gone.** The audit found the problem was wider than this entry recorded: **six** private copies existed, not four (`useAreaPagination`, `useGoalPagination`, `useDeletedGoalPagination`, `useNotePagination`, `useProjectPagination` and Assets' `usePagination`), and **two** collections had no accumulating paginator at all. All six now delegate to the shared hook.
  - **The two absences are closed too.** `/meetings` and `/reviews` paginated by NAVIGATING to the next page — replacing the list and discarding the owner's scroll position — and Meetings labelled that control "Load more", which is not what it did. Both now use the shared hook and the shared `LoadMore` affordance, so all eight collections behave identically.
  - **Notes' extra guard was subsumed, not dropped.** `useNotePagination` additionally discarded a page whose echoed `state` no longer matched the selected lifecycle view. The shared request-scoped rule is strictly stronger — it discards ANY response issued under a previous scope, not only one whose state field happens to disagree.
  - **Evidence.** [`test/unit/load-more/useKeysetPagination.test.tsx`](../../test/unit/load-more/useKeysetPagination.test.tsx) covers accumulation, boundary de-duplication, a retryable failed page that does not advance the cursor, and the exhausted no-op; [`e2e/ux-01-daily-driver.spec.ts`](../../e2e/ux-01-daily-driver.spec.ts) asserts neither collection offers a page-replacing link any more; the existing Projects/Goals/Areas/Notes/People/Assets "Load more" journeys pass unchanged.
- **Related roadmap item.** [UX-01](../roadmap/ROADMAP_V2.md#-ux-01--daily-driver-ux-ui-and-product-polish) (resolved here); [X-02](../roadmap/ROADMAP_V2.md#-x-02--saved-views--cross-module-filters) (where collection-wide list behaviour is next revisited); tracked alongside [DEBT-01](#-debt-01--duplicate-card-implementations-per-module--p2) as another per-module duplication of one idea.

### ☐ DEBT-49 — Two filter models coexist: DS-07 expressions and the Tasks declarative configuration — P3
- **Current issue.** The product now contains two filter models. ### ☑ DEBT-63 — "Load more" could silently drop a page — P1 — **RESOLVED 2026-08-01**

- **Filed as a test-timing curiosity. It was a product defect.** The first draft of this entry recorded two keyset-pagination component tests failing "only under heavy machine load", noted CI was green, and deliberately declined to widen their waits without a reproduction. Then the same family failed on CI on a dedicated runner (`NotesCollection.test.tsx`, run 30715617556), which falsified the "only under load" reading and forced a real diagnosis.
- **The diagnosis, and the experiment that settled it.** Reproduced locally at ~1 run in 12 by running the Notes and Projects collection suites together. The decisive step was widening the wait to **8 seconds**: it still failed. That rules out slowness — the page was never delivered at all. Tracing the shared hook then showed the mechanism exactly, and there were **two** independent drop paths:
  1. **The mount-time scope reset.** `useEffect` runs after paint, so a `findBy*` (which resolves during render) followed by a click could land *before* React flushed the mount effect. The reset then ran for the first time with a request already stamped, cleared `requested.current`, and the page that arrived was discarded as belonging to a previous scope.
  2. **The premature failure branch.** `fetcher.load()` does not synchronously leave the idle state, so `state === "idle" && data === undefined` has two meanings — "settled with nothing" and "has not started yet". The branch treated them alike, so it fired in the window between stamping the request and the fetcher going `loading`, set the retry state and cleared the request; the real page was then dropped.
- **What the owner saw.** Click "Load more"; the spinner clears; nothing is added; the cursor does not advance. A second click works. **All eight collections share this hook** (Areas, Goals, Notes, Projects, People, Assets, Meetings, Reviews), so it was product-wide.
- **The fix.** Reset only on a genuine scope CHANGE (compared by value, seeded with the mount scope) rather than whenever the effect happens to run; and gate the failure branch on a `started` flag that is only set once the fetcher has actually left idle. Neither weakens the DEBT-45 rule this hook exists to encode — a scope that genuinely changes still discards an in-flight request, which is exactly what must happen.
- **Measured before and after,** running the Notes + Projects collection suites together: **1 failure in 12** before; **5 in 30** with only the first fix (which is why both were needed, and how the second was found); **0 in 40** with both. The full unit suite then passed **3/3 consecutive runs (3128 tests)**.
- **Regression coverage, stated honestly.** The two collection suites that reproduced it are the guard: they exercise the path and went from intermittently red to 40/40 green. An attempt to add a dedicated repeated-journey test to `useKeysetPagination.test.tsx` was **removed rather than shipped** — it passed 5/5 against the *pre-fix* hook, so it guarded nothing, and a check that cannot fail is worse than no check because it reads as protection. The race only opens in the larger collection component trees, not in the isolated harness.
- **The lesson worth keeping.** `test/unit/load-more/useKeysetPagination.test.tsx` already carried a widened 5-second wait with a comment blaming "a fully-parallel suite run". That widening was masking this defect. **An intermittent test that is fixed by waiting longer has not been diagnosed** — the 8-second experiment is what turned a suspected flake into a found bug, and it cost one command.
- **Related roadmap item.** [UX-01](../roadmap/ROADMAP_V2.md#-ux-01--daily-driver-ux-ui-and-product-polish) (which introduced the shared hook); [DEBT-45 (pagination)](#-debt-45--keyset-paginators-can-consume-a-revalidated-fetcher-page-after-a-scope-reset--p3--resolved-2026-08-01), whose rule this preserves.

### ☐ DEBT-61 — An export is not a point-in-time snapshot, and a busy workspace can produce a slightly incoherent one — P3

- **Current issue.** [X-04](../roadmap/ROADMAP_V2.md#-x-04--export--data-portability) reads the workspace through a SEQUENCE of bounded statements. Each statement sees a consistent database, but the sequence does not: a write committed while the export is running is visible to the collections read after it and absent from those read before. A task created mid-export can therefore land in `entities` with no `taskDetails` row, or a link can name an entity that had not yet been read — which the snapshot validator would reject, failing the export rather than shipping an inconsistent file.
- **Why it was accepted.** D1 exposes no cross-statement snapshot for this read pattern through the Workers binding, so the alternatives were to claim a guarantee that does not exist, or to state the real one. - **Desired future state.** If D1's Sessions API (or an equivalent read-snapshot mechanism) becomes usable from the Workers binding for a multi-statement read, bind the whole export to one snapshot and change `meta.consistency` to say so. Until then the honest statement is the correct behaviour, not a workaround.
- **Evidence.** [`build-snapshot.ts`](../../app/platform/export/build-snapshot.ts) (the sequential read and the reasoning), `SNAPSHOT_CONSISTENCY` in [`workspace-snapshot.ts`](../../app/kernel/export/workspace-snapshot.ts), and the validator's referential-integrity checks in [`snapshot-validation.ts`](../../app/kernel/export/snapshot-validation.ts).
- **Related roadmap item.** [SET-02](../roadmap/ROADMAP_V2.md#-set-02--backup--restore) — a scheduled backup runs unattended and hits this window more often than a hand-pressed export does, so it is the item that should decide whether the mitigation is still enough.

### ☐ DEBT-62 — The whole export is assembled in memory, so it is bounded rather than unbounded — P3

### ☐ DEBT-67 — Seven curated themes is more choice than one owner needs — P3

- **Current issue.** THEME-02 added the Modern pair, taking the registry to **seven** curated themes plus the `system` appearance mode ([`theme-preference.ts`](../../app/kernel/preferences/theme-preference.ts), [`tokens.css`](../../app/styles/tokens.css)). Three of them — Eucalypt, Coastal and Ember — are *character* themes: single light palettes that differ from Daly Light mainly in hue. There is now visible overlap, most obviously between **Daly Light**, **Modern Light**, **Coastal** and **Eucalypt**, all of which are light themes with a cool-to-neutral surround and a restrained blue-green or green accent.
- **Impact.** Cost is carried in three places, none of them the owner's data: a settings list long enough that the choice takes thought rather than a glance; a maintenance tax where **every new colour token must be authored eight times** (seven themes plus the duplicated `prefers-color-scheme` dark block) and pass the full contrast harness in each; and CI time in the whole-registry sweeps (`assets-ownership.spec.ts` now walks seven themes, and the THEME-01 surface matrix is seven × six). It is friction and drag, not a defect — every theme is complete, distinct and AA-clean today.
- **Desired future state.** A registry of roughly **four**: one default pair and one alternative pair, or a default plus two genuinely distinct characters. The obvious candidates for retirement are the character themes whose distance from a shipped default is smallest, but **that is a product judgement, not a mechanical one, and it is deliberately not being made here.** Removing a theme takes a choice away from an owner who may already be on it, and this change existed to add a theme, not to delete four.
- **How a removal would have to be done, when it is decided.** The registry entry, the `tokens.css` block and the TS colour map come out together; the `theme` CHECK is narrowed by a further rebuild migration; and `parseThemePreference` already degrades a retired value to the default rather than leaving the document unstyled — there is an E2E test for exactly that case, so a removal has a proven safe landing. It should also be announced in the release notes rather than discovered by an owner whose theme silently changed.
- **What the DS-14 foundation learned, and it is evidence for this entry rather than against it (2026-08-03).** The foundation authored **21 new colour tokens** — `surface-page`, the neutral absence pill pair, `divider-subtle`, and six Area accents each with a tint pair — **eight times**, and recomposed the light neutral ramp of **five** themes to satisfy the elevation contract. The tax this entry predicts is real and was paid in full. It was also **survivable**, and specifically because it was mechanical: the values are generated from stated rules and asserted by a test that enumerates the registry, so seven themes cost seven rows of a table rather than seven independent judgements. That is the honest shape of this debt — it is drag on every token-level change, not a coherence failure, and it does not get worse per theme so much as it gets *longer*.
- **This was deliberately NOT acted on by DS-14.** A restyle that quietly deletes four themes to make its own work smaller is a product decision taken for an engineering reason. No theme was exempted from the contract and none was removed; the recommendation stands here, undecided, for whoever decides it on its merits.
- **Closing condition.** Either a decision recorded in an ADR to keep all seven (with the maintenance cost accepted explicitly), or a consolidation shipped with the removal path above and the acceptance matrix updated to the reduced set.
- **Related roadmap item.** [THEME-02](../roadmap/ROADMAP_V2_1.md#-theme-02--the-modern-visual-system); [DS-14](../roadmap/ROADMAP_V2_1.md#-ds-14--whole-application-visual-overhaul) (paid the tax, did not act on the recommendation).

### ☐ DEBT-68 — Logging out does not clear the device's offline data automatically — P2

- **Current issue.** DalyHub's sign-out is a Cloudflare Access sign-out: the session ends at the edge, and there is no client-side hook that runs before it does. So the PWA milestone's local-data clearing is an explicit control (`/settings?section=offline` → *Reset offline data*), not something that happens on logout. After logging out, a previously synced snapshot and any queued captures remain in IndexedDB on that device until the owner clears them, the browser evicts them, or a different identity signs in (which deletes the previous namespace's snapshot but deliberately keeps its queued captures).
- **Impact.** On a shared or borrowed device, "I logged out" does not mean "my data is off this machine". The Settings surface states this plainly and the behaviour is documented, so nothing is misrepresented — but the owner has to take a second action they may not think to take.
- **Desired future state.** A sign-out path DalyHub owns end to end: an in-app control that clears the offline database and DalyHub's caches BEFORE redirecting to the Access logout endpoint, plus a "clear offline data when I sign out" preference for anyone who wants it unconditional. This belongs with [SET-03](../roadmap/ROADMAP_V2_1.md#-set-03--account--security), which is already the owner-facing session/identity surface.
- **Closing condition.** Signing out through the DalyHub control leaves no `dalyhub-offline` database and no `dalyhub-*` cache on the device, proven by a Playwright assertion, with queued captures either synced first or explicitly confirmed as discarded.
- **Related roadmap item.** [SET-03](../roadmap/ROADMAP_V2_1.md#-set-03--account--security).

### ☐ DEBT-69 — Offline capture receipts accumulate with no prune — P3

- **Current issue.** `offline_capture_receipts` (migration `0027`) is written once per replayed offline capture and never deleted. Its purpose is to survive the retry window — minutes, not years — but nothing removes an old row. `created_at` is indexed for exactly this, and the table is bounded by how many captures the owner actually makes offline, so this is small and slow-growing rather than dangerous.
- **Impact.** Unbounded row growth in a table with no reader after its retry window. At a realistic capture rate it is measured in kilobytes a year; the debt is that "unbounded" is still unbounded.
- **Desired future state.** An age-based prune (delete receipts older than a documented horizon) attached to whatever scheduled maintenance DalyHub gains first — the V2.0.1 backup workflow is the obvious host.
- **Closing condition.** Receipts older than the horizon are removed, with a kernel test proving a receipt inside the horizon still prevents a duplicate.
- **Related roadmap item.** [PWA/offline](../development/PWA_AND_OFFLINE.md#11-known-limitations) (follow-on).

### ☐ DEBT-71 — A replayed capture whose Worker died mid-creation cannot be resolved automatically — P2

- **Current issue.** Offline capture replay claims an idempotency key in `offline_capture_receipts` *before* the module creates anything, and finishes the receipt with the created id afterwards. D1 has no interactive transaction that can span the module's own creation code, so a Worker that dies between those two writes leaves a receipt whose outcome is undecidable: the create may have committed just before the process ended, or never run at all. DalyHub retires the key rather than guessing (`capture-receipts.server.ts`), so no duplicate is ever created — but the owner is asked to check whether the capture arrived, and the queued capture is marked as needing attention rather than syncing.
- **Impact.** Rare (it needs a Worker to die inside a one-round-trip window) and never destructive: the capture's text stays on the device and nothing is duplicated. The debt is that a resolvable situation is handed to the owner.
- **Desired future state.** Make the creation itself idempotent so there is no second write to lose: derive the created record's primary key from the idempotency key, so replay is an `INSERT … ON CONFLICT DO NOTHING` against the record table and the receipt becomes an optimisation rather than the guarantee. That is a change to how the three modules mint ids, which is why it was not folded into the PWA milestone.
- **Closing condition.** A kernel test kills the request between create and receipt completion, replays the same key, and asserts exactly one record exists and the replay reports its id — with no owner-facing "check whether this arrived" message.
- **Related roadmap item.** [PWA/offline](../development/PWA_AND_OFFLINE.md#11-known-limitations) (follow-on).

### ☐ DEBT-70 — Hydrated offline rendering is not covered by automation — P2

- **Current issue.** `e2e/pwa-offline.spec.ts` runs against the development server, because it is the only Playwright server with an authenticated session (the production-mode server is deliberately fail-closed, which is its own test). A Vite dev server has no hashed bundles to precache, so an offline reload renders the cached shell DOCUMENT but cannot hydrate it. The suite therefore proves the service worker's runtime behaviour and asserts the snapshot and queue directly in IndexedDB, but not that the fully hydrated offline application renders from the precached production bundle.
- **Impact.** The single most user-visible offline behaviour — "I opened DalyHub on a plane and it worked" — rests on the manual device checklist rather than on CI.
- **Desired future state.** A third Playwright server: the real production build served with the development authenticator, so the precached production bundle can be exercised offline. It needs a build directory that is not shared with the fail-closed preview server.
- **Closing condition.** A Playwright test loads the production bundle authenticated, goes offline, reloads, and asserts the offline snapshot renders from IndexedDB with hydration complete.
- **Related roadmap item.** [PWA/offline](../development/PWA_AND_OFFLINE.md#10-testing) (follow-on).

### ☑ DEBT-72 — Card-on-tint is a phone-native pattern and its behaviour at 1440px and above is unproven — P2 — **RESOLVED 2026-08-03**

- **Current issue.** [DS-14](../roadmap/ROADMAP_V2_1.md#-ds-14--whole-application-visual-overhaul) restyles every DalyHub surface to **card-on-tint** — a tinted page canvas with cards raised above it ([`DS_14_OVERHAUL_BRIEF.md §1`](../design/DS_14_OVERHAUL_BRIEF.md), [ADR-068](../decisions/ARCHITECTURE_DECISIONS.md#adr-068-ds-14--the-card-on-tint-direction-its-elevation-contract-two-density-presets-derived-area-colour-and-a-single-commit-rollback)). That pattern is **native to the phone**, where it earns its keep: a narrow viewport shows one or two cards, the tint reads as a surround, and the card reads as the thing you are holding. It is not established that it survives being scaled up. At 1440px and above the same rules produce many cards on a large field of tint, and the risks are specific and nameable — the canvas becoming a large expanse of flat colour rather than a surround; a grid of cards reading as a scattered board instead of one contained workspace, which is the property [`DESIGN_SYSTEM.md → Surface & boundaries`](../design/DESIGN_SYSTEM.md#surface--boundaries) exists to hold; and the ΔL\* ≥ 3 separation being comfortable on a 6-inch panel and either invisible or banded across a wide, bright display.
- **The gap is in the verification, not only in the design.** [`DS_14_OVERHAUL_BRIEF.md §10`](../design/DS_14_OVERHAUL_BRIEF.md) sets DS-14's verification widths at **320, 375, 390, 430, 768, 1280, 1440** — six of the seven are phone or tablet, and the widest is 1440. The repository's existing responsive regression ([`e2e/responsive.spec.ts`](../../e2e/responsive.spec.ts), DS-11) already sweeps **320 / 375 / 390 / 768 / 1024 / 1440 / 2560**, so DS-14's own matrix stops short of a width the product is already tested at. Overflow-free at 2560px is not the same claim as *coherent* at 2560px, and neither is asserted for card-on-tint today.
- **Impact.** The owner's daily driver is a desktop. If the pattern does not hold at width, it is discovered after seven PRs have restyled every module rather than after one, and the discovery is aesthetic — meaning no test fails and nothing goes red. This is the single largest unproven assumption in DS-14.
- **Resolution evidence.** The rejected staged delivery model is not an active
  product process. The wide-desktop risk is handled as implementation evidence:
  real screenshots and responsive checks at desktop widths, plus automated surface
  hierarchy assertions for card, page and raised layers. If the pattern fails in
  review, the fix belongs in the visual PR that introduced the defect, not in a
  deferred owner-process gate.
- **Status: RESOLVED 2026-08-03 — answered inside DS-14.** The answer arrived during implementation, and **it was a real defect, not a false alarm**: an uncapped collection row at 1440px puts the record's title at one end and its status pill at the other with roughly a thousand pixels between them — the "stretched mobile application" this entry's third named risk describes, reached by a route the entry did not predict (row geometry rather than tint expanse).
- **The fix, and why it is the general one.** A content measure on **collections**, not only on prose: `.dh-collection__content` is capped at `--dh-width-wide` and aligned to the inline START rather than centred, because the navigation rail is on the left and a centred column drifts away from it as the viewport grows. That is [ADR-069 decision 7](../decisions/ARCHITECTURE_DECISIONS.md#adr-069-ds-14-applied--the-group-is-the-card-the-shared-boundary-is-the-region-and-what-a-whole-application-restyle-cost-in-one-pr). The other two named risks did not materialise: the group-is-the-card decision means a wide viewport shows ONE card containing many rows rather than a scattered board of many cards, which also removes the large-flat-tint concern — the tint is a surround, not a field.
- **What is still not claimed.** The measured ΔL\* (3.41–4.72, [`THEME_ACCEPTANCE_MATRIX.md §9.2`](../design/THEME_ACCEPTANCE_MATRIX.md)) is verified numerically and reviewed in captured screenshots at 1280 and 1440 in all seven themes, light and dark. That is a screenshot and automation claim, not a claim about personal taste after extended use.
- **Desired future state.** Card-on-tint verified at desktop widths on real content, with the evidence in [`THEME_ACCEPTANCE_MATRIX.md`](../design/THEME_ACCEPTANCE_MATRIX.md) as a DS-14 section, and DS-14's verification widths extended to include 2560 so its matrix is not narrower than the suite the product already runs.
- **Closing condition — met.** The wide-desktop failure mode was identified and fixed inside DS-14; the DS-14 acceptance section is written; `responsive.spec.ts`'s 320–2560 sweep passes over every restyled surface. The assumption was tested, which is what this entry was raised for.
- **Related roadmap item.** [DS-14](../roadmap/ROADMAP_V2_1.md#-ds-14--whole-application-visual-overhaul).

### ☐ DEBT-73 — Area colour is derived from rank, so the owner cannot choose it and a permanent deletion repaints later Areas — P3

- **Current issue.** [ADR-068 decision 5](../decisions/ARCHITECTURE_DECISIONS.md#adr-068-ds-14--the-card-on-tint-direction-its-elevation-contract-two-density-presets-derived-area-colour-and-a-single-commit-rollback) derives an Area's accent rather than storing it: rank the workspace's Areas by `(created_at, id)` and take `area-accent-((rank mod 6) + 1)`. Nothing is persisted — `area_details` ([migration `0013`](../../migrations/0013_create_area_details.sql)) holds one nullable `archived_at` and states outright that it is not a second identity model, and there is no colour column on `entities`. Derivation was chosen because it needs **no migration**, and because the alternatives are worse: a hash of the id collides with ≈91% probability at five Areas over a six-colour ramp, and a stored colour needs both a migration and an owner-facing picker that [`DS_14_OVERHAUL_BRIEF.md §9`](../design/DS_14_OVERHAUL_BRIEF.md) explicitly puts out of scope.
- **Impact.** Two properties derivation cannot give. **The owner cannot choose an Area's colour** — if Health comes out orange and that reads wrong to the person whose life it is, there is no way to change it. And **a permanent Area deletion repaints every Area created after it**, because rank depends on the set. That is bounded on purpose (rank is computed over every `area` row regardless of lifecycle state, so archiving and soft-deleting change nothing, and only the irreversible typed-confirmation delete shifts anything) but it is still an Area changing colour as a side effect of a different Area being removed. Beyond six Areas the ramp wraps and two Areas share an accent; that is tolerable only because [`§10`](../design/DS_14_OVERHAUL_BRIEF.md) forbids colour as the sole carrier of meaning — the dot always has an accessible name and always sits beside the Area's own title.
- **Desired future state.** An **optional** stored colour: a nullable accent column on the Area detail slice, defaulting to null, with the derived value used whenever it is null. That keeps every existing Area's colour exactly as it is on the day it ships, makes owner choice additive rather than a reset, and pins a chosen colour against the deletion shift. It belongs wherever Area settings next get owner-facing surface, not inside a restyle.
- **How it would be done, so the path is not re-derived.** One additive migration on `area_details` in the precedent that table already sets (nullable column, no backfill, absence means the default); the accent resolver gains a stored-value branch ahead of the rank computation; the picker offers only the six ramp accents so [`§2`](../design/DS_14_OVERHAUL_BRIEF.md)'s colour discipline holds and no owner can select a role colour; and the DS-14 invariant test covers the stored values by construction, because it already asserts every `area-accent-*` pairing in every theme.
- **Closing condition.** An Area's colour can be set and cleared from the Area record, a cleared value falls back to the derived one, a stored value survives another Area's permanent deletion, and the accent contrast assertions still pass in all seven themes.
- **Related roadmap item.** [DS-14](../roadmap/ROADMAP_V2_1.md#-ds-14--whole-application-visual-overhaul) (follow-on), landing with [SET-03](../roadmap/ROADMAP_V2_1.md#-set-03--account--security) or whichever item next opens Area settings.

### ☐ DEBT-76 — A Chromium renderer segfault fails Playwright shards non-deterministically, and `retries: 0` turns it into a red build — P2

- **Current issue.** `chrome-headless-shell-1228` on the `ubuntu-24.04` runner image intermittently dies mid-run with `Received signal 11 SEGV_MAPERR 0000000001b0` (`cr2: 0x1b0`, identical stack every time). The test that happens to be executing then fails with `browser.newContext: Target page, context or browser has been closed` — **no assertion has failed and nothing is wrong with the code**, but the shard exits non-zero and `CI Gate` goes red because it aggregates `playwright`.
- **It is not new, and it is not any one branch's.** The same signature appears on **`main` at [`6aba3ae`](https://github.com/acedaly/DalyHub-V2/commit/6aba3ae) (run 30802345484, shard 1, `/people` axe scan)** and on [PR #106](https://github.com/acedaly/DalyHub-V2/pull/106) (run 30841044978, shards 3 and 5, `diary` and `people`). It was briefly and wrongly attributed to a scroll-driven animation in that PR; the `main` occurrence predates that code, which is what settles it. The crash favours axe scans and repeated-viewport-resize tests — long-lived pages doing heavy layout work — but has hit at least three different specs.
- **Impact.** **Four of the ten most recent `main` CI runs are red**, and a red `main` is corrosive in a specific way: it stops being information. Once a maintainer learns that failures are usually noise, a real regression rides in behind one, and the cost of the flake is paid by the change that follows it rather than by the flake itself. It also makes every PR's CI a coin toss on 14 shards — the more shards, the likelier at least one crashes.
- **Desired future state.** A shard that fails only because the browser died retries and passes, and a shard that fails because an assertion failed still goes red immediately.
- **How it would be done, so the path is not re-derived.** The repository sets `retries: 0` in [`playwright.config.ts`](../../playwright.config.ts) deliberately — "no retries that could mask flakiness" (ADR-008/ADR-016), and that instinct is right for **assertion** flakiness. A browser-process crash is a different class: it is not the product being non-deterministic, it is the harness dying. The narrow change is `retries: process.env.CI ? 1 : 0`, which leaves local runs strict; Playwright's HTML report marks a retried test `flaky` rather than `passed`, so the noise stays **visible** instead of being swallowed — which is the property that makes this different from simply weakening the gate. A stricter alternative is to keep `retries: 0` and pin/upgrade the Playwright browser build, since the crash is specific to `chrome-headless-shell-1228`; that is the better fix if an upgrade makes it go away, and it should be tried first.
- **Closing condition.** Ten consecutive `main` runs green, with any retried test still reported as flaky rather than silently passing.
- **Related roadmap item.** None — CI hygiene. Surfaced by [DS-14](../roadmap/ROADMAP_V2_1.md#-ds-14--whole-application-visual-overhaul).
